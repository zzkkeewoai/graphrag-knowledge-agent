# 企业域 GraphRAG 评测与调优报告

> 日期：2026-11-04　模型：deepseek-chat　embedding：BAAI/bge-small-zh-v1.5

## 一、目标

给「GraphRAG 多 Agent 知识检索系统」换一个知识域：从**项目文档**换成**模拟中厂的企业制度库**，
并建立一套能定位问题的评测闭环。

原系统的评测是 Ragas + 40 道项目域题（A项目 / 张伟 / 技术栈）。本次不替换它，而是**新增企业域**，
原 40 题保留为回归集。

## 二、数据契约：从 7 类扩到 14 类

| 层 | 原有 | 新增 | 为什么 |
|---|---|---|---|
| 实体 | 项目/人员/技术栈/里程碑/部门/文档/概念 | 条款/阈值/时限/流程/角色/组织/系统 | 「5万元」「次年3月31日」「二级审批」原 schema 无处可放，只能塞「概念」 |
| 关系 | 使用/依赖/领导/属于/前置/后置/引用/包含 | 审批/适用于/截止于/依据/替代/负责/访问 | 每缺一个关系，最像的那个就会被占满 |

**只增不改**：枚举值是写入图谱的数据契约，改值 = 旧节点全部对不上，且抽取器 prompt 是动态拼的。

### 关键设计：条款再化

一条带条件的规则抽成「条款」节点，让多个条件挂在它身上：

```
第2.2条 —依据→ 5万元 / 50万元
第2.2条 —审批→ 部门负责人 / 财务总监
第2.2条 —适用于→ 采购付款
```

不这么做，三元组表达不了 n 元关系，「哪个阈值对应哪个审批人」会丢。

## 三、语料：4 篇骨架

| 文件 | 内容 | 服务的题型 |
|---|---|---|
| org.md | 12 部门 / 汇报关系 / 角色 / 外部合作方 | 组织类、多跳 |
| systems.md | 8 个业务系统 + 权限 + 故障响应 | 「走哪个系统」 |
| approval_matrix.md | 15 条审批规则（带条号） | 数值、审批链 |
| permissions.md | 密级 + 访问范围 + 违规处理 | 越权、拒答 |

**写作原则（踩坑换来的）**：

1. 一句话只表达一个关系——枚举句会生成大量噪声边（实测一句话产生 16 条「包含」）
2. 不用代词——「其负责人」导致汇报关系整句丢失
3. 顺着已有关系词写——「向…汇报」没有对应关系，改成「总经理 领导 经理」
4. 一段讲一件事——12 个部门挤在一段，具体事实的检索分数被平均掉

## 四、结果

| 数据集 | 题量 | 准确率 | 说明 |
|---|---|---|---|
| simco_eval（调优集） | 20 | **20/20** | 迭代过程中反复使用 |
| holdout20（开发集） | 20 | **20/20** | 用于定位问题 |
| holdout2（验收集） | 20 | **20/20** | 最终验证 |
| 原项目域 40 题 | 40 | 未回归验证 | 待做 |

延迟：中位 1.6–6 秒（含 1–2 次 LLM 调用）。

## 五、13 个问题与修复（按发现顺序）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 回答是"🔍 找到 3 条相关信息" | `.env` 里 `USE_LLM_ANSWER=false` | 改为 true |
| 2 | 第 3 问返回第 2 问的答案 | 语义缓存跨问题误命中 | 评测期关闭缓存 |
| 3 | 采购问题召回出差补贴 | 英文 embedding（MiniLM）编码中文 | 换 bge-small-zh + **重灌** |
| 4 | 「什么时候生效」答不出 | 灌库脚本跳过了元数据块 | 元数据入库 |
| 5 | 同上，仍答不出 | 元数据块里没有文档标题，检索对不上 | 拼上《标题》 |
| 6 | 证据只给 3 条 | `orchestrator:216` 写死 `top_k=3`，`RERANK_TOP_K` 没用上 | 改成读配置 |
| 7 | 「60万谁审批」拒答 | 验证器做字面实体匹配，证据写「50万及以上」 | 数值类跳过实体匹配 |
| 8 | 「年终奖」用通用常识回答 | global 分支 prompt 无"仅依据资料"约束 | 补边界 |
| 9 | 「财务部下设哪几个组」走 global | LLM 兜底路由把列举题判成聚合题 | 关闭 LLM 路由，规则兜底 |
| 10 | 「薪酬发放用哪个系统」拒答 | 实体匹配对中文太脆弱 | 改相关性阈值 0.55（负对照：相关 0.59-0.61 / 无关 0.32-0.48） |
| 11 | 含答案的块排向量第 4 却进不了上下文 | RRF 融合中图谱结果挤占向量结果 | 融合保底：补 2 条未入选的向量结果 |
| 12 | 同上，保底无效 | 保底取的是向量前 2 名（本已在融合里） | 改为取"未入选的前 2 条" |
| 13 | 向量只召回 5 条 | `retrieve()` 用默认 `top_k=5`，`VECTOR_TOP_K` 没用上 | 传 `Config.VECTOR_TOP_K` |

**模式总结**：13 个里只有 3 个是算法逻辑问题，其余全是**配置没接线 / 数据没入库 / 文档结构**。

## 六、已知局限

- 验收集只有 20 题，单题权重 5%
- holdout20 与 holdout2 在修复过程中被查看过，严格意义上已不是盲测集
- 证据阈值 0.55 只由 5 个对照样本定出，换语料或换 embedding 必须重测
- 原项目域 40 题未做回归，扩域是否损害旧能力尚未验证
- 语料仅 4 篇，覆盖财务/HR/IT/组织，缺合同、售后、生产

## 七、复现

```bash
# 1. 灌库（建图 + 建向量）
python tests/ingest_simco.py --reset

# 2. 起服务
./run_api.ps1

# 3. 评测
python tests/run_eval.py --file datasets/holdout2.jsonl --out runs/final.json
python tests/show_eval.py runs/final.json
```

## 八、调试工具箱

| 脚本 | 用途 |
|---|---|
| `debug_retrieval.py` | 向量检索召回了什么、目标块排第几 |
| `debug_fusion.py` | 图谱/向量/融合三路结果对比 |
| `check_graph.py` | 图谱实体分布、再化节点连通性、两跳可达 |
| `ask_simco.py` | 单问，可看 trace |
| `show_eval.py` | 评测结果汇总 |

**这些工具比模型本身更值钱**——它们让"效果不好"变成"第几层坏了"。
