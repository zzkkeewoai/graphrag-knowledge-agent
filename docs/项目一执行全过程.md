# 项目一：一次请求是怎么执行的（真实 trace + 代码地图）

> 全部数字来自实际运行（2026-11-08，414 块语料，domain=pdf）。

---

## 一、先看结果：两条路径

### 路径 A · 正常回答（3.1 秒）

问题：「对外担保超过净资产 50% 需要谁审批？」

```
orchestrator_pipeline        3082.7ms   route=local
├─ router                      0.0ms    route=local
├─ local_retrieval          1653.4ms    attempt=1  document_count=8
├─ evidence_validation         1.0ms    evidence_status=sufficient  next_action=answer
└─ answer_generation        1423.3ms    answer_length=95
```

**答案**：根据《对外担保管理制度》第三章第十五条，……须经股东会审批，且必须经董事会审议通过后……

### 路径 B · 拒答（3.3 秒，多一步）

问题：「今天天气怎么样？」

```
orchestrator_pipeline                 
├─ router                             
├─ local_retrieval           document_count=8
├─ evidence_validation       evidence_status=insufficient  next_action=targeted_graph
├─ targeted_graph_retrieval           ← 定向补召回一次
├─ evidence_validation       evidence_status=insufficient  next_action=refuse
└─ （refuse 节点）                      steps=2
```

**答案**：当前知识库中的信息不足以回答您的问题。

## 二、逐个节点：谁在跑、跑什么、坏了什么症状

| 节点 | 代码位置 | 输入 → 输出 | 耗时 | 坏了会怎样 |
|---|---|---|---|---|
| **router** | `orchestrator_v2.py::router_node` → `Router.route()` | query → `local`/`global` | **0ms**（纯规则） | 全走错分支，答非所问 |
| **local_retrieval** | `local_node` → `LocalAgent.execute` → `HybridRetriever.retrieve` | query → 8 个文档块 | **1.6s** | 证据找不到 / 找到错的 |
| **evidence_validation** | `evidence_validator_node` → `EvidenceValidator.validate` | 8 块 → sufficient / insufficient | **1ms**（纯规则） | 该拒不拒（编）/ 不该拒却拒 |
| **targeted_graph_retrieval** | `targeted_graph_node` | 缺的实体 → 补查询 | 只在 insufficient 时跑 | 补不到就白跑一次 |
| **answer_generation** | `answer_node` → `AnswerAgent.generate` | 8 块 → 答案文本 | **1.4s**（LLM） | 答错 / 答一半 / 编 |

### 时间花在哪（这句话面试常问）

```
检索 1.6s + 生成 1.4s = 3.0s，规则判断只有 1ms
```

**结论：延迟几乎全在"检索"和"LLM 生成"两头，规则层可以忽略不计。**
所以优化只有两个方向：**少检索、少生成**（缓存/拒答/降上下文条数）。

## 三、local_retrieval 内部：1.6 秒里发生了什么

这一层是项目一的**核心**，面试追问全在这。顺序是：

```
① 域过滤准备      按 docs 的 domain 推断（entity_domain 映射，懒加载 0.5s，之后复用）
② 图谱召回        _graph_retrieve(query, hops=2)      ← Neo4j 查两跳邻居
③ 向量召回        _vector_retrieve(query, fetch_k)    ← embedding + 余弦
④ BM25 召回       _bm25_retrieve(query, fetch_k)      ← 字符二元组倒排
⑤ 域过滤          三路各自 keep(doc_id)
⑥ RRF 融合        reciprocal_rank_fusion([graph, vector, bm25])
⑦ 保底配额        向量全量 + BM25 前 2 强制入队
⑧ 拼 text_map     候选 → 原文（截断 1500 字）
⑨ 精排            reranker.rerank(top_k = RERANK_TOP_K)
```

**每一步的"坏症状"**（这就是你四层定位的根据）：

| 步骤 | 坏了会怎样 | 怎么查 |
|---|---|---|
| ② 图谱 | 多跳题答不出 | `check_graph.py` 看两跳可达 |
| ③ 向量 | 相似语义召回不到 | `debug_retrieval.py` 看排名 |
| ④ BM25 | 精确术语召回不到 | 同上 |
| ⑥ 融合 | 原文被挤出窗口 | `debug_fusion.py` 看三路 |
| ⑦ 保底 | 同上（配额没生效） | 看日志 `[保底] 补入 N 条` |
| ⑨ 精排 | 证据被砍掉 | trace 里 `document_count` 变小 |

## 四、一个容易混的点：项目里有**两层拒答**

这是面试官可能钻的地方，你最好主动分清。

### 第一层：规则拒答（validator 判 insufficient）

```
证据相关性 < 阈值（0.40）→ insufficient → 补召回 → 仍不足 → refuse
```

**触发条件**：问题与知识库**完全不相关**（"今天天气" top1 只有 0.32）。
**症状**：`steps=2`，trace 里能看到 `targeted_graph` 和两次 `evidence_validation`。

### 第二层：生成层拒答（LLM 自己说不知道）

```
证据相关性 ≥ 阈值 → 判 sufficient → 交给 LLM → LLM 说"信息不足"
```

**触发条件**：**相关但答案不在里面**（"2026 上半年营收"——检索到的都是 2025 年报）。
**症状**：`steps=1`，trace 里 `evidence_status=sufficient`，但答案仍是拒答。

**为什么要分清**：因为阈值调到 0.40 之后，**大部分拒答已经变成第二层**——规则层只挡真正无关的问题。这是取舍，不是 bug。

## 五、自己手动触发每条路径（自测用）

```powershell
# 路径 A：正常回答
python tests/ask_simco.py --q "对外担保超过净资产50%需要谁审批？" --trace

# 路径 B1：规则拒答（完全不相关，看 targeted_graph）

# 路径 B2：生成层拒答（相关但没答案，steps=1 但答案是拒答）
python tests/ask_simco.py --q "公司2026年上半年营业收入是多少" --trace

# 看检索内部：目标块排第几
python tests/debug_retrieval.py "对外担保超过净资产50%" --top 6

# 看融合内部：三路各给了什么
python tests/debug_fusion.py "对外担保超过净资产50%" --needle 净资产
```

## 六、口述版（面试照这个说，40 秒）

「一次请求四个节点。

**router** 是纯规则，0 毫秒，判断走 local 还是 global。
**local_retrieval** 最重，1.6 秒——三路召回加 RRF 融合，再加保底配额，最后精排到 8 条。
**evidence_validation** 1 毫秒，纯规则判断证据够不够；不够就补召回一次，还不足就走到拒答。
**answer_generation** 1.4 秒，调 LLM 生成。

所以延迟几乎全在检索和生成两头，规则层可以忽略——优化只能往"少检索、少生成"走。」
