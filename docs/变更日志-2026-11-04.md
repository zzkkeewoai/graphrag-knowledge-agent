## 一、Schema 扩展

### 1. 实体 7 → 13，关系 8 → 13

**改了什么**：`graph_schema.py` 新增 6 个实体（条款/阈值/时限/流程/角色/组织）、5 个关系（审批/适用于/截止于/依据/替代）。

**为什么**：拿 5 个企业句子试归类，只有「人员」能用。`5万元`「次年3月31日」「二级审批」全部无处可放，只能塞进「概念」——图里会堆满同类型节点，检索无法区分。

**为什么只增不改**：
1. 枚举值是图谱的数据契约，改值 = 库里的旧节点全部对不上，要做数据迁移；
2. 抽取器 prompt 是 `", ".join(e.value for e in EntityType)` 动态拼的，改枚举立刻改变模型行为；
3. 旧的项目域 40 题还要当回归集，改类型等于把回归基线一起弄坏。

**验证**：`python -c "len(EntityType)"` → 13 / 13。

### 2. 试抽 3 篇小文档 → 命中 1/3

**改了什么**：写 `tests/try_extract.py`，三篇各考一件事（审批链 / 时限 / 版本替代）。

**为什么**：改 schema 只是"允许它抽"，不代表"它真的会抽"。要先验证，再批量造语料。

**结果**：1/3。新类型几乎没被用上。

### 3. 修 few-shot + 类型定义 + 删误导指令

**改了什么**：
- `_build_few_shot()` 加示例 3（审批链）、示例 4（时限与版本）；
- system prompt 加"实体类型的含义""关系类型的含义"两段人话定义；
- 删掉「优先抽取"核心实体"（项目、人员、技术栈）之间的关系」。

**为什么**：最后那条不是倾向，是**明确命令**——模型被要求优先抽项目域的东西。few-shot 又全是项目域例子，双重强化。

**验证**：3/3。prompt 从 1400 → 3985 字符（有成本，见后）。

### 4. 写 `org.md` → 抽出 94 条，其中「包含」56 条

**为什么是这个数**：文档里有「公司设 12 个一级部门：A、B、C…」这类枚举句，一句生成十几条「公司—包含→X」边。

**为什么是问题**：这些边不承载业务信息，却会让多跳检索多走冤枉路、社区划分变差。**边的数量不是问题，边的语义错了才是。**

### 5. 删枚举句 → 包含 56 → 9，但「适用于」4 → 40

**改了什么**：把两处冒号列举改成一句话概述。

**结果**：包含掉了，但「适用于」暴涨。

**为什么**：删掉一个出口，模型从最近的另一个出口挤出来，总边数几乎没变（94→87）。**噪声会搬家，不会消失**——除非改产生噪声的句子。

### 6. 加关系「负责」+ 示例

**改了什么**：`RESPONSIBLE_FOR = "负责"`，prompt 补定义，示例 3 补一条「采购部 负责 采购执行」。

**为什么**：那 40 条「适用于」全是「部门→职责」，被错误占用。缺一个关系，最像的那个就会被占满。

**结果**：适用于 40 → 0，负责 45。

### 7. 写 `systems.md` → 技术栈 40、「适用于」21

**为什么技术栈是 40**：schema 里没有「系统」，「ERP / OA / CRM」只能归到「技术栈」，和 Python、Neo4j 混在一起。检索时无法区和"项目用什么框架"和"流程走哪个系统"。

**为什么适用于又回来**：权限句「部门可以访问系统」没有对应关系。

### 8. 加实体「系统」+ 关系「访问」+ 示例 5

**结果**：技术栈 40 → 0，系统 40；访问 10 出现；适用于仍有 21。

### 9. 看样本 → 「适用于」21 是合法的，只改定义

**改了什么**：把定义从「条款 → 对象」扩成「条款或系统 → 对象/流程」。

**为什么**：21 条全是 `系统 —适用于→ 流程`（"HRM 系统用于薪酬发放"），语义正确。**数字异常先看样本：样本对了改定义，样本错了才改结构。**

**这是唯一一次"虚惊"**——没加类型。前四次都是真问题。

## 二、语料与建库

### 10. 写 `approval_matrix.md` → 条件配对丢失

**现象**：抽出 17 条审批边、6 个阈值，但「5-50 万 → 财务总监」这个配对没了。

**为什么**：三元组只能挂两个东西，表达不了 n 元关系（条件）。不处理的话，问「30 万谁审批」会同时返回三个审批人。

### 11. 加条号 + 示例 6（条款再化）

**改了什么**：文档每条规则前加「第 2.1 条」；few-shot 加示例展示「条款节点承载阈值/审批人/流程」。

**为什么**：工业解法是 reification——把「一条规则」变成节点。**不需要新类型，已有的「条款」就是天然的再化节点。** 前提是文档给每条规则编号（现实中制度本来就有条号）。

**验证**：五条边挂在同一个「第2.2条」上，配对保住了。

### 12. 写 `ingest_simco.py`（文档 → 图 + 向量）

**为什么单独写**：原来的 `seed_demo_data.py` 是硬编码几条三元组，不能读文档。

### 13. Milvus 拉不下来 → 写 `local_vector_store.py`

**现象**：`minio` 镜像从两个加速器都返回 403。

**改了什么**：写一个接口完全一致的本地实现（numpy + npz 文件 + 余弦检索），改 `api.py` 一处导入与构造。

**为什么可行**：项目对向量库只有三个需求——建集合 / 写入 / top-k 检索。8GB 机器跑四个容器本来就紧。
**为什么不改调用方**：同接口 = 换一行构造就能切，业务代码零改动。

### 14. `check_graph.py` 验证图结构

**结果**：207 节点 / 233 边；`第2.2条` 五条边齐全；两跳「采购付款→第2.2条→财务总监」可达。

### 15. 发现：条款节点只有名字，没有原文

**为什么重要**：`_entity_row()` 只写 head/tail/relation/confidence，不存 `source_chunk`。图知道"第2.2条依据5万元"，但不知道第2.2条到底写了什么。

**结论**：**这解释了架构为什么必须是 hybrid**——图负责关系，向量负责内容，缺一个都不行。

## 三、端到端与评测

### 16. 写 20 题评测集 + `run_eval.py`

**为什么分四类**：单跳（定位）、多跳（串联）、拒答（不编）、时效（日期判断）。

### 17. 首跑 11/20 → 修判分 → 13/20

**改了什么**：拒答关键词补「不足以」「不足够」「没有足够」。

**为什么**：模型拒答措辞自由（"信息不足以回答"），只认几个词会把正确拒答判成错。

### 18. 延迟 251ms → 发现 `.env` 里 `USE_LLM_ANSWER=false`

**现象**：所有回答都是「🔍 找到 3 条相关信息」，中位延迟 251ms。

**为什么**：配置默认关闭生成，answer 字段是检索原文的模板拼接。一次 LLM 调用不可能 251ms——**延迟是最诚实的指标**。

**改了什么**：`.env` 改 `USE_LLM_ANSWER=true`、`USE_LLM_ROUTER=true`、`USE_SEMANTIC_CACHE=false`。

### 19. 16/20；t01「什么时候生效」答不出

**根因一**：灌库脚本把文档头部的元数据块（`- 生效日期：…`）当噪声跳过了，那条信息从没进库。
**根因二**：补进去后仍答不出——块里只有「文档编号/生效日期」，没有「审批权限矩阵」这几个字，检索对不上号。
**修法**：元数据入库 + 拼上文档标题 `《LH-FIN-2026-010 审批权限矩阵》`。

### 20. 证据只给 3 条

**根因**：`orchestrator_v2.py:216` 写死 `top_k=3`，`Config.RERANK_TOP_K` 定义了却没用。
**修法**：`top_k=Config.RERANK_TOP_K`（并把配置调到 5）。

**这是第一次「配置没接线」**。

### 21. m01/m02 多跳拒答 → 数值类跳过字面匹配

**根因**：验证器从问题里抽实体，在证据里做字面匹配。问题问「60 万」，证据写「50 万元及以上」——**永远匹配不上**。
**修法**：查询含数字+单位（万/元/天/日/%）时跳过字面匹配，交给生成阶段判断（生成 prompt 已有"信息不足请说明"的约束）。

**边界**：这只是"不再提前拦"，不是"实现了区间推理"。

### 22. r02「年终奖」用通用常识编答案

**根因**：global 分支 prompt 只写"根据以下全局分析总结回答"，没有"仅依据资料"的约束。
**修法**：加「仅根据以下资料回答，禁止使用通用常识补充；没有就说知识库中没有相关规定」。

## 四、独立验证（防过拟合）

### 24. holdout20（新 20 题）→ 75%

**为什么**：前 20 题被"看着答案修"了八轮，95% 不可信。

**诊断三条**：
- `v08`/`v18` 路由到 global → LLM 兜底路由把「列举型」问题判成「聚合型」；
- `v13`/`v19` 证据不足 → 实体匹配对中文太脆弱；
- `v10` 抽取错 → 文档里「其负责人…直接向总经理汇报」有代词 + 一句话两个关系。

### 25. 关 LLM 路由 → 85%

**为什么**：规则路由里 global 关键词是「总结/对比/统计/所有…」，两个问题一个都没命中，按规则本该走 local。**规则默认 local，比 LLM 猜更稳。**

### 26. 证据阈值 0.55 → 95%

**改了什么**：新增"检索最高分 ≥ 阈值即判 sufficient"，替代字面实体匹配。

**阈值怎么来的（负对照）**：
| 类型 | 最高分 |
|---|---|
| 相关问题 | 0.588 / 0.614 |
| 无关问题 | 0.320（今天天气）/ 0.480（有班车吗） |

取 0.55 能把两者分开。**注释里写死：换语料或换 embedding 必须重测。**

1. 去掉代词「其负责人」→ 拆成两句；

### 30. 融合保底（第一次写错）

**根因**：RRF 只按排名融合，图谱一路结果数量远多于向量一路，向量结果被整体挤出窗口。实测「含 1200 人」的块向量排第 4，融合后消失。

## 五、今天学到的五条（可复述）

1. **噪声会搬家，不会消失。** 删掉一种错误归因，它会挤进最近的那个关系类型。要么补类型，要么改产生它的句子。
2. **数字异常先看样本。** 21 条「适用于」看着像 bug，样本一看全是合法的——差点多加一个没必要的类型，让 schema 膨胀。
3. **配置写了不等于生效。** 一天踩了两次（`RERANK_TOP_K`、`VECTOR_TOP_K`）。排查手法：改一个参数，看结果有没有变；没变就是没接线。
4. **"答不出来"要分四层定位**：入库 → 召回 → 融合 → 生成。每一层都有对应的调试脚本，先看数据再改代码。
5. **判断什么时候停，比能不能修更重要。** 为了救 2 道题把向量宽度翻倍，结果撞超时——边际收益递减时该收手，把问题记进"已知局限"。
